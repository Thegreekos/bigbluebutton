# Same-server acceptance harness (Chromium)

These tests use dedicated meetings only. Keep the BBB package versions unchanged while establishing a baseline. Supply `BBB_URL=https://HOST/bigbluebutton/` and `BBB_SECRET` through the environment, not in source or logs. The ignored `.env` contains placeholders only. Run with `--project=Chromium --workers=1 --reporter=line`; the setup project validates the API. Playwright Chromium and `core/media/{video.y4m,fakespeech.wav}` must be available. Do not run `killConnection()` on the BBB host: it changes host-wide iptables rules.

- `api/acceptance.spec.ts`: signed API create/end, moderator + attendee join, real chat delivery, audio modal dismissed by `data-test`.
- `user/user.spec.ts -g 'Rapid lock-settings saves'`: three OFF/ON/mic-OFF rounds, actual attendee textarea, unique sent/received messages, attendee reload. Each save waits for attendee's server-side permission to settle; no fixed sleep between ON and the next save. An RC4 failure can stop later rounds: that is a failed permission assertion, not a selector error.
- `audio/audio.spec.ts -g 'Push-to-talk release'`: six independent cases (normal, chat focus, Ctrl, Alt, window blur, synthetic visibilitychange); check local LiveKit mic publication and remote participant's unmuted publisher as well as the next cycle. Synthetic visibilitychange is not a real OS background-tab transition.
- `options/audioProcessingModeTrack.spec.ts -g 'keeps the same microphone publication'`: local publication and second participant's live subscribed RTP packet counter must keep growing after switching mode.
- `reconnection/reconnection.spec.ts -g 'Reconnection.*(Chat|Audio)'`: drops only the test page's GraphQL WebSocket, waits for reconnection and chat delivery; no firewall modifications.
- `screenshare/screenshare.spec.ts -g 'Webcams fill the media area|Hidden presentation stays hidden'`: regressions #25872 and #25871.
- Existing smoke cases: `chat/chat.spec.ts`, `webcam/webcam.spec.ts`, `presentation/presentation.spec.ts`, `whiteboard/whiteboard.spec.ts`, `polling/polling.spec.ts`, `screenshare/screenshare.spec.ts` (filter for `Send public message|Shares webcam$|Skip slide$|Upload single presentation|Draw with pencil|Create poll$|Start and Stop Share screen`).
- `recording/acceptance.spec.ts`: record=true; fake mic, two participants, webcam, PDF upload, screen share, chat, end; wait for presentation format from getRecordings; verify archive/process/publish markers and ffprobe duration/audio/video for the *new recording only*, then validate the unmodified API playback URL and browser content. Requires the test runner on the BBB server (`/var/bigbluebutton` phase/media probes and `ffprobe`). An invalid host in the published URL is a real FAIL; never replace it with the test host. Media connection timeouts are also FAIL, not a skip.

RC4 baseline observed 2026-10-02: API/chat, audio processing RTP, reconnection, webcam/presentation/whiteboard/poll/start-stop share PASS. #25871/#25872 fail after share stops at presentation-state assertions. #25622 fails publication/mute/next-cycle checks; #25896 fails at attendee chat disabled following OFF→ON (2/2 repeated). Recording reached archive/process/publish with nonzero video, audio and deskshare once, but its published URL used the unresolvable `bigbluebutton.example.com`; repeated runs also stalled at webcam connection. Consequently **do not claim playback or pilot acceptance** from this baseline.
